# 000 — Internationalization Strategy

## Current State

Open Knowledge Studio is **English only**. No i18n framework is included in the runtime dependencies, consistent with the project's zero-dependency rule. All UI text, labels, tooltips, and aria-labels are hardcoded in English.

## Design Constraints

- **Zero runtime dependencies** — No `react-i18next`, `react-intl`, or any i18n library may be added to `package.json`.
- **Browser-native APIs** — The [`Intl`](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Intl) namespace is available in all modern browsers and should be used for number, date, and currency formatting.
- **CDN-loaded libs** — KaTeX, Mermaid, and Leaflet have their own i18n capabilities but are not currently configured for locale switching.

## Recommended Approach

### 1. Number & Date Formatting (Intl API)

The `Intl` API is already available natively. Example usage for future i18n:

```typescript
const dateFormatter = new Intl.DateTimeFormat(navigator.language, {
  dateStyle: 'medium',
  timeStyle: 'short',
});
const numberFormatter = new Intl.NumberFormat(navigator.language);
```

This covers date displays in messages, timestamps in the UI, and numeric formatting in the Epi Map and Metrics dashboard — no library needed.

### 2. UI Text Translation (JSON Files)

For UI strings (labels, buttons, tooltips), a **JSON translation file** approach is recommended:

```
public/
  locales/
    en.json
    bn.json
    fr.json
    ...
```

Each file contains a flat or nested key-value mapping:

```json
{
  "app.title": "Open Knowledge Studio",
  "app.tagline": "Research. Write. Analyze.",
  "agent.coordinator.name": "Coordinator",
  "agent.coordinator.description": "Orchestrates multi-agent debate workflows"
}
```

Translation resolution would be a simple lookup function (no framework):

```typescript
function t(key: string, params?: Record<string, string>): string {
  let value = translations[key] ?? key;
  if (params) {
    Object.entries(params).forEach(([k, v]) => {
      value = value.replace(`{${k}}`, v);
    });
  }
  return value;
}
```

### 3. Locale Detection

Detect the user's preferred language via:

```typescript
const locale = navigator.language; // e.g., "en-US", "fr-FR", "bn-BD"
const baseLang = locale.split('-')[0]; // "en", "fr", "bn"
```

Fall back to `en` if the detected locale has no corresponding translation file.

## Right-to-Left (RTL) Support

RTL languages (Arabic, Hebrew, Persian, Urdu) require:

- `dir="rtl"` attribute on `<html>` when RTL locale is detected
- CSS logical properties (`margin-inline-start` instead of `margin-left`, etc.) — Tailwind 4.x utilities are predominantly LTR-focused; RTL-aware classes would need custom additions
- KaTeX and Mermaid have partial RTL support; Leaflet maps are unaffected
- RTL testing would require browser-level locale configuration in Playwright

No current implementation. RTL support is deferred until a contributor with RTL language expertise can validate the approach.

## Community Contributions

Translations are a natural entry point for community contributions. Suggested workflow:

1. Contributor creates `public/locales/{lang}.json` based on `en.json`
2. PR is reviewed for completeness (all keys present) and accuracy
3. Locale is added to the auto-detect fallback chain
4. A language selector UI (dropdown or flag icon) could be added when 3+ locales exist

## Timeline

There is **no scheduled timeline** for i18n implementation. It depends on community demand and contributor availability. The architecture is designed to accommodate i18n without breaking the zero-dependency rule.
